# ADR-0027: Data export as a ZIP sent by the bot; account deletion is immediate and hard
- Status: accepted (owner, 2026-10-27)
- Date: 2026-10-27
## Context
ST-09 and NF-03 require that a person can export their own data (CSV/JSON) and delete their account. The data includes sealed values (🌸 status, rest-period kind, diary notes; ADR-0016) that the owner's export must show in plain form. Constraints: Cloud Run throttles CPU outside requests, so nothing may run after the response (ADR-0011/0018); 512 MiB memory, a 60 s request timeout; ≤ $5/month; a webhook reply can't upload files (ADR-0012); the Mini App runs in Telegram WebViews, where `<a download>` of a blob is unreliable and `WebApp.downloadFile` exists only on newer clients and fetches a URL without our `Authorization` header. Every per-account table already cascades from `account` (`progression_event.marked_by` is SET NULL). Backups: a weekly `pg_dump` kept 90 days until this decision, plus Supabase's daily platform backups. The field-encryption keyring is global, not per account. Spec: `docs/specs/ST-09-export-delete.md`.
## Decision
- **Format:** one ZIP: `data.json` (everything, versioned schema `tristhana.export/1`, ISO dates, UTC instants, wall times with their IANA zone), `days.csv` (one row per day), `rest_periods.csv`, `progression.csv` (UTF-8 with BOM) and a localized `README.txt`. Machine codes stay English (the export vocabulary says `no_practice`, not the internal `skipped`); each code has a localized label column (`status_label`, `kind_label`, `*_name` with simple Latin asana names in EN and the catalog's Cyrillic transliteration in RU). Seals are opened for the owner, so 🌸 appears with its true value (the README says so; a "🌸 as rest" variant is deferred to ST-06); an unreadable seal is kept as `unreadable: true` and reads as rest, never 🌸. `marked_by` is `self`/`teacher`/`unknown`, never a name. Stored facts only: derived day off, moon days and pause days are not exported as days; the README explains this supportively.
- **Delivery:** built synchronously inside the request (one read-only REPEATABLE READ transaction, stdlib `json`/`csv`/`zipfile`, lazy-imported) and sent by the bot with `sendDocument` to the person's own private chat, whether the bot or the Mini App asked. The application emits it through the `Notifier` port (`send_export`); only the Telegram adapter knows about documents. No Cloud Storage object, no signed URL, no file over HTTP.
- **Rate limit:** one export per 10 minutes per account, claimed atomically on `account.export_claimed_at` and released if sending fails.
- **Deletion:** after a two-step confirmation (the final bot button is bound to the account and expires after 10 minutes; the Mini App uses Telegram's native confirm), one `DELETE FROM account` removes everything through the FK cascades. No grace period, no tombstone: a later message, tap or Mini App open creates a fresh, empty account. Writes racing a delete hit an FK violation that maps to `AccountGone` (the tick skips the send; the API answers 410).
- **Backups and logs:** no crypto-shredding. One log line `account deleted <uuid>` per deletion is the list to re-delete after any restore; backups age out on their lifecycle, which is shortened from 90 to 30 days (owner applies the cloud change) to match the 30-day log retention. The user-facing copy states the chat history and the 30-day backup window honestly.
- **Coverage rule:** a test fails if a table with an FK to `account` is neither exported nor explicitly excluded, or doesn't cascade / set null. Future tables (teacher links, shalas, bookings) must choose.
## Consequences
- No new infrastructure, dependency or job; one nullable column (migration 0016). Works on every Telegram client. A heavy 25-year user's file is about 2 MB zipped and takes about 1 s; the worst case (a 2000-character note every day) stays under Telegram's 50 MB upload limit, the timeout and memory.
- The exported file, diary notes included, sits in the person's Telegram chat (Telegram's cloud) until they delete it; the copy says so.
- Deletion can't be undone; the export-first button is the safety net. A reminder claimed seconds before the delete may still be sent (at-most-once ledger).
- Restoring a backup can bring deleted accounts back; the runbook re-deletes them from the deletion log lines, which Cloud Logging keeps 30 days, so the weekly dump lifecycle is set to 30 days (owner decision 8, 2026-10-27). Supabase's own platform backups follow its plan's retention.
- Per-account encryption keys stay unneeded: a wrapped per-account key would be in the same backups, so it would not shorten exposure.
- A future web client needs its own download path (e.g. a streaming endpoint with its own auth); the JSON schema is shared.
## Alternatives considered
- **Mini App `downloadFile` + a short-lived signed URL to a streaming endpoint:** keeps the file out of the chat, but needs a signing secret or token table and fails on older clients. Kept as the later web-client path.
- **Cloud Storage object + signed URL:** a bucket, lifecycle rules and a second copy of sensitive data at rest; no gain at this size.
- **Asynchronous export (job, then notify):** impossible without background CPU on Cloud Run, and unnecessary at a few seconds.
- **Grace period (soft delete for 7–30 days):** every read, the tick and auth would have to respect a pending state, plus a purge job and an undo screen. Too much for a hobby project; the export covers regret.
- **A tombstone of the Telegram id** to stop silent re-creation: keeps a derivative of personal data after deletion; rejected.
- **Typed confirmation ("DELETE"):** awkward on phones and in two languages; the bound, expiring two-step button is enough.
- **JSON only / CSV only:** JSON alone is unfriendly for spreadsheets; CSV alone can't hold the nested structure cleanly. Both in one ZIP cost nothing extra.
