# ADR-0016: Field-level encryption for sensitive data (XChaCha20-Poly1305, projected plain column)
- Status: accepted
- Date: 2026-10-18
## Context
PR-01 adds the day status, and one value, ladies' holiday, is sensitive. WH-02 says others see "Rest day", WH-04 requires field-level encryption at rest, and CLAUDE.md requires application-level encryption for the diary, check-in notes and ladies' holiday. Later features (PR-06 check-ins, PR-07 diary) will need the same mechanism. Constraints: Supabase free tier (the DB provider and any dump must not see plain values), < 300 ms per tap, ≤ $5/month, an image budget of 250 MB (currently 242 MB), and teacher/shala aggregates (ST-06, ST-08) that must count ladies' holiday as rest without decrypting anything. Spec: `docs/specs/PR-01-day-status.md`.
## Decision
- **Cipher:** XChaCha20-Poly1305 (IETF AEAD) from libsodium via **PyNaCl** (`nacl.bindings`; imported only in `infrastructure/crypto.py`, preloaded at startup). Ciphertext = `key id (1 byte) ‖ nonce (24 random bytes) ‖ ciphertext + tag (16)`. Random 24-byte nonces make nonce reuse a non-issue. AAD binds a value to its place: table, column, and the row's identity (for `day_log`: `account_id ‖ local_date`), so a ciphertext can't be copied to another row or account.
- **Keys:** a keyring in one Secret Manager secret, `field-encryption-keys` = `"<id>:<base64 32 bytes>[,…]"`, first entry active for writes, all entries usable for reads. Only the runtime SA can read it. The owner generates the key locally and keeps a copy in a password manager. Rotation: prepend a new key, deploy, then (later) a one-off job re-seals old rows and the old key is dropped.
- **Projected plain column + sealed truth:** the plain column holds what others may see (`status = 'rest'`); the true value is sealed in a separate column (`sealed_status`) on **every** row with that public value, padded to the same length. Rest and ladies rows are indistinguishable in the DB. A CHECK forbids the sensitive value in the plain column. Teacher views and aggregates read only the plain column and never need the key.
- **Failure mode:** a value that can't be opened (lost or retired key, tampering) degrades to its public value (`rest`) with a warning carrying only the account uuid. No key configured: sealed reads/writes fail as "temporarily unavailable"; prod refuses to start with a database but no keys.
- Encryption lives in infrastructure (repository adapters); the domain decides *what* is private (`public_status`), the application sees plain domain values.
## Consequences
A DB dump or the Supabase console shows ladies' holiday as rest; the owner's own views decrypt in app code (microseconds per row; a year has at most ~100 sealed rows). Losing the key loses only the distinction ladies/rest, never a day. One more secret, one more dependency (PyNaCl, +4.9 MB measured; the image stays under the 250 MB budget). Exports (ST-09) and per-teacher disclosure (WH-02) decrypt through the same cipher. Diary and check-in notes reuse the format with their own AAD.
## Alternatives considered
Plain `ladies` value (violates WH-04, visible in dumps); an encrypted marker only on ladies rows (its presence leaks the fact); Postgres `pgcrypto` (the key travels in SQL and may reach DB logs); Cloud KMS per request (network latency and cost per tap; envelope encryption with a KMS-wrapped data key stays possible later without changing the row format); AES-256-GCM via `cryptography` (most standard, but +16 MB measured would break the 250 MB image budget; revisit if `cryptography` arrives anyway, e.g. for JWT); PyNaCl `SecretBox` (no AAD); a stream cipher built on stdlib HMAC (avoids the dependency, but is our own construction).
