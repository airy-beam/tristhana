# ADR-0024: Check-ins stored plain in their own table, visible only to the owner by policy
- Status: accepted (owner, 2026-10-27)
- Date: 2026-10-27
## Context
PR-06 adds an after-practice check-in: mood, energy and effort (1–5 each) plus optional tags (stiff, light, scattered…). In 05 Domain Model's privacy matrix, check-ins are **owner only**: hidden from teachers by default, shown to a teacher only after an opt-in, and never included in shala aggregates. CLAUDE.md and ADR-0016 require application-level encryption for "diary, check-in **notes** and ladies' holiday". ST-05 (Phase 3) wants trends: energy/effort over time and correlation with moon phase and weekday. We need to decide whether the scores and tags are sealed (ADR-0016) or stored plain, and where they live. Constraints: < 300 ms per tap with one statement per tap, stateless bot callbacks (ADR-0008), and the smallest design that doesn't block ST-05. Spec: `docs/specs/PR-06-check-in.md`.
## Decision
- **Own table `check_in`**, one row per practice slot `(account_id, local_date, slot)`, FK → `day_log` on delete cascade. It exists only on a Practiced day, under the same "day is practiced" guard as `practice` (PR-02), and it is deleted in the same statement when the day changes to another status. It is separate from `practice`, so "Remove details" doesn't delete a check-in, and a check-in doesn't need any details.
- **Scores and tags are stored plain**: `mood`, `energy`, `effort` as `smallint` 1–5 (nullable) and `tags text[]` holding natural keys (validated in the domain, with no DB CHECK on the values, so adding a tag needs no migration). This follows the precedent of sick/travel and practice details, which are plain (PR-01, PR-02).
- **Who can see it is enforced in `application/` policies, not at rest.** Every read is the caller's own data today. Teacher views (ST-06) **omit check-ins entirely**: a teacher view must never show "check-in missing" or whether one exists. A future ST-06 opt-in is **per teacher and off by default**, and its scope (mood vs body tags only) is decided at ST-06. Shala aggregates never read `check_in`. ST-06/08 must have a test that proves this.
- The owner accepted plain storage knowing that mood and soreness may count as health-adjacent data under GDPR (2026-10-27). The sealed design below stays the documented fallback.
- **Free text is always sealed.** If a note is ever added to a check-in (otherwise it goes to PR-07's diary), it uses ADR-0016's format with AAD `b"check_in.sealed_note|" + account_id.bytes + local_date.isoformat() + b"|" + slot`. Including the slot means a note can't be moved between practices on the same day.
- The tag vocabulary is a domain `StrEnum` with labels in Fluent (`.ftl`). It is not seed YAML, because labels must live in `.ftl` (ADR-0007) and the list only changes with a release.
## Consequences
Each tap is one plain `INSERT … ON CONFLICT DO UPDATE` with a per-field patch. A tag toggle is an atomic `array_append`/`array_remove`. DB CHECKs guard the ranges. Reads add one LEFT JOIN to the existing day query. ST-05 can use plain SQL (`GROUP BY` weekday, a join to `moon_day`, `unnest(tags)`) or compute in `domain/stats.py` (ADR-0020). The downside: a DB dump or the Supabase console shows a person's mood and energy for each practiced day, linked to their account uuid (no names, since we store only the first name). It never shows ladies' holiday, because check-ins exist only on practiced days and the tag list deliberately has no menstrual, pain or injury tags (injury belongs in the Sick/Injury status). If the owner later wants these values sealed, a one-off job can seal them into a `sealed` column and drop the plain ones. Bot callbacks would then have to carry the full check-in state, which still fits in 64 bytes (see Alternatives).
## Alternatives considered
- **Seal the whole check-in as one fixed-length blob** (padded JSON, about 200 bytes, AAD `check_in.sealed|account|date|slot`). It is better protected at rest, and the matrix needs no plain consumer: ST-05 can decrypt about 366 rows per year in microseconds. The costs: no partial SQL update, so the bot's callbacks must carry the full state (`k1:s:20261018:342:sl…`), and last write wins between two open messages; no DB CHECKs; no SQL analytics. This is the recommended fallback if the owner treats mood as health data.
- **Columns on `practice`**: no new table, but "Remove details" (`DELETE practice`) would also delete the check-in, and an empty practice row would have to exist just to hold one.
- **Attach to the day, not the slot**: this breaks when a second practice per day arrives (morning Mysore plus evening pranayama). A slot costs nothing now.
- **Tags in `data/seed/*.yaml`**: data-driven, but the labels would sit outside Fluent, or the keys and labels would be split across two places. Revisit when teachers or users can define their own tags.

## Note for ST-05 (code review, 2026-10-27)
Reads of `check_in` for trends must join `day_log` on `status = 'practiced'`, like `SqlDayLogRepository._range`. A rare race between a status change and a check-in save can leave a row behind on a day that is no longer Practiced; joined reads never see it, and re-practicing the day deletes it.
