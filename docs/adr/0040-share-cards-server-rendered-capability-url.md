# ADR-0040: Share cards are rendered server-side with Pillow, kept 24 h as PNG in Postgres and served at a capability URL on the API
- Status: accepted 2026-11-09 (owner, with the spec's Q197–Q211)
- Date: 2026-11-09
## Context
ST-07 asks for shareable cards (month recap, year heatmap, new asana / next series begins, practice counts) in story 9:16 and square formats, shared with Telegram's `shareToStory` and downloadable as PNG. `shareToStory(media_url)` and `downloadFile(url, name)` (Bot API 7.8 / 8.0) both take a **public HTTPS URL**; `shareToStory` exists only on mobile clients, `downloadFile` only on newer ones, and `<a download>` of a blob is unreliable in Telegram WebViews (ADR-0027). ADR-0020 requires every non-owner view, share cards included, to project days before the stats rules so 🌸 can never appear. Constraints: ≤ $5/month; backend image ≤ 250 MB; Mini App initial JS 144.1 of 150 KB gzip; < 300 ms p50 per tap; CPU only inside requests on Cloud Run; `*.run.app` and `*.web.app` are confirmed reachable from RU/KZ (Q14), `storage.googleapis.com` is not tested. `04 Architecture` planned Cloud Storage for share cards. Spec: `docs/specs/ST-07-share-cards.md`.
## Decision
- **Render on the server.** `application` builds a card value from data it has already projected to **two tones** (practice / no practice: every rest-like status, "No practice" and unmarked days merge, so neither a 🌸 pattern nor an unlogged signal is readable; owner Q209) plus moon rings taken only from the account's stored calendar for its effective location (MD-02 resolved, never recomputed, no default city), and passes it to a `CardRenderer` port. The adapter `infrastructure/cards/pillow_renderer.py` is the only module importing **Pillow** (lazy, not preloaded, run in a worker thread), with bundled OFL fonts (Noto Serif Display + Noto Sans subsets: Latin, IAST, Cyrillic). Cards contain no emoji glyphs (moon days are drawn rings), so they look the same on every client. Copy comes from a backend `card.ftl` (en/ru).
- **Render once, store briefly.** `POST /api/v1/me/share-cards` renders one format and inserts the PNG into `share_card` (migration 0026) under a SHA-256 of a 128-bit random token, with `expires_at` = now + 24 h, a rate limit of 50 per account per rolling 24 h checked in the same statement, and cascade on account delete. The tick prunes expired rows. The table is excluded from the ST-09 export.
- **Serve from the API at a capability URL**: `GET /share/v1/{token}.png`, outside `/api/v1` auth and OpenAPI, one PK read, `Cache-Control: public, max-age=86400, immutable`, the same 404 for unknown and expired; the token is masked in logs like the calendar feed's (ADR-0036). The Mini App previews this URL (CSP `img-src` adds the API origin) and hands it to `shareToStory` / `downloadFile`.
- **Fallback delivery through the bot**: "Send to my chat" sends the stored PNG as a photo via a `Notifier.send_card_photo` port (as ST-09 sends exports), once per card. This covers desktop and older clients and forwarding to friends.
- No Cloud Storage bucket for share cards; the Files row in `04 Architecture` changes accordingly.
## Consequences
- Privacy is enforced in one place (application projection, tested); nothing user-supplied (pixels or text) is ever hosted, so the URL can't be abused as free image hosting. What the user previews is byte-for-byte what is shared.
- +≈ 15 MB image (Pillow + fonts), to be measured against the 250 MB budget; the first card after a cold start pays the Pillow import (~0.1–0.2 s). Each create costs ~100–300 ms CPU (measured in TDD); fetches cost no CPU.
- Postgres holds a few short-lived ~100 KB blobs (bounded by the TTL and rate limit, far under the Supabase free tier); one migration, no new secret, no new cloud resource, no owner ☁️ step besides the normal deploy.
- Mini App bundle: only buttons and a lazy share chunk (~3 KB); no canvas code, no font download in the WebView.
- Cards are drawn in Python, separately from the Mini App's SVG heatmap: two drawings of the same grid. The numbers still come from one domain (ADR-0020).
- A card link works for 24 h for anyone who has it; the content is meant to be public and carries no name.
## Alternatives considered
- **Client-side canvas in the Mini App + upload to the backend/GCS:** zero backend dependency and native fonts, but the backend would host arbitrary user-supplied pixels publicly, privacy projection would be presentational in the client, emoji and fonts differ per platform, the share chunk grows (canvas drawing, a brand font), and an upload path plus storage is still needed for `shareToStory`.
- **Cloud Storage object (public or signed URL), maybe via a Cloud Run volume mount:** standard for files, but a new bucket, IAM, public access or a signing key, lifecycle rules, and a third domain whose RU/KZ reachability is untested; no gain at this size.
- **Render on every fetch from a stateless signed token (no table):** no migration, but a new signing secret, CPU per fetch by anyone holding the URL, and the shared image could differ from the preview if the log changes in between.
- **SVG templates rasterised with resvg, or headless Chrome:** resvg is smaller to author but a less proven Python binding; Chrome/Playwright is hundreds of MB, far over budget.
- **Upload the photo to Telegram and reuse its file URL:** Bot API file URLs embed the bot token, so they can never be given to a client.
