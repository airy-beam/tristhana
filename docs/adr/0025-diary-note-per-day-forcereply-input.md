# ADR-0025: Diary notes: one sealed note per day, independent of the status; bot input by ForceReply
- Status: accepted (owner, 2026-10-27)
- Date: 2026-10-27
## Context
PR-07 adds a free-text diary note. CLAUDE.md and ADR-0016 require diary text to be encrypted at the application level; the 05 privacy matrix makes it owner-only (teacher sharing "per entry" later). People write on rest, moon and 🌸 days too, and a stored note must never reveal a 🌸 day (stored as plain `rest` + seal, ADR-0016). The bot is stateless (ADR-0008: state in callback data, < 300 ms per tap, one statement where possible), but a note is free text, which callback data can't carry. Spec: `docs/specs/PR-07-diary-note.md`.
## Decision
- **Storage:** own table `diary_note(account_id, local_date)` PK, FK → `account` on delete cascade, **no FK to `day_log` and no status column**. One note per local day, on any day up to today, logged or not. Status changes, clearing the day and rest periods never touch it; removal is explicit. So the plain row looks the same whatever the day's status.
- **Sealed** with ADR-0016's format in `sealed_text bytea`, AAD `b"diary_note.sealed_text|" + account_id.bytes + local_date.isoformat()`. An unreadable seal reads as "present but unreadable" (row kept, can be overwritten or removed). Max 2000 code points of plain text; DB CHECK on the sealed length. No server-side search or previews; reads decrypt only in the owner's `GetDays` (one statement via aggregated subqueries) and the bot's note screen.
- **Bot input by ForceReply:** `[✏️ Write]` sends a new prompt whose first line is a fixed token `📓 YYYY-MM-DD`, with `ForceReply`. A message is saved as a note only if it **replies to a message sent by this bot** whose text starts with the token. The account always comes from the sender (private chats only), and the token holds only a date, so a reply can only write the sender's own day. A reply to an old prompt writes that prompt's day (explicit, replaces). Everything else keeps today's `fallback-text`. Edits aren't subscribed (`allowed_updates` unchanged). After a reply the bot confirms briefly and **never echoes the text**; removal is confirmed first and tells the person that earlier chat messages stay until they delete them in Telegram. The Mini App is the second writing surface.
- **No processing of note text:** no parsing, keyword detection, inferences or advice; a note never changes progression (the last given asana). Note text or a "has note" marker appears only on single-day screens, never in week/stats/summary views or pushes.
## Consequences
No new state, no pending-input reads, 0 statements to prompt and 1 upsert to save. The visible ISO token is slightly technical, and the user must reply (Telegram's ForceReply sets that up automatically; if they dismiss it, the text gets the fallback). Replacing (not appending) means a reply to an old prompt overwrites the note written since; screen N shows the current text first, so this is visible. Ciphertext length reveals the approximate note length (no padding; accepted). A note on a day later changed to another status stays, which is the intent. Key rotation keeps old keys in the keyring while rows sealed with them exist (the first byte is the key id). Teacher views (ST-06) and exports (ST-09) must go through `can_view_diary`; ST-09 decrypts.
## Alternatives considered
- **Per practice slot** (like check-ins): loses rest-day diaries and must delete notes on status change (data loss after a mis-tap).
- **A pending-input row or `account.awaiting_note_for` column** (ADR-0008's `bot_dialog`): free with the middleware's account read, and works without a reply, but hidden state means an unrelated message typed later silently becomes a diary entry; it needs a TTL and an extra write per prompt.
- **A hidden `text_link` entity as the marker** (e.g. a Mini App deep link over the emoji): invisible and tappable, but needs a direct-link app name and `startapp` handling; a possible later upgrade of the same mechanism.
- **Mini App-only writing:** simplest backend, but bot-only users couldn't write, and PR-06 promised a note button on the check-in screen.
- **Padding the plaintext to fixed buckets:** hides the length, costs up to ×2 storage; not worth it for owner-only text.
