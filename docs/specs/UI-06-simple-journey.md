# UI-06: simple journey (a front door, a Today screen, one Menu; then the Mini App in three tabs)

- Status: **accepted** (owner, 2026-11-16: the scope in §1–§2, and Q310–Q316 in §11 all as recommended) · Size **L**, five pull requests · Phase 3 (before the public launch)
- Requirements: **UI-06** (new: the whole journey is simple enough to need no guide). Changes UI-01 (`/start`, `/help`), **retires the bot half of UI-02** (owner), touches PR-01/02/06/10, ID-03/04/06, SC-01/03, NT-01, UI-05. ID-03 stays: roles are derived from data, never stored.
- Related: ADR-0005, 0008, 0012, 0021, 0029, 0030, 0031, 0033, 0042, 0043. New, proposed: **ADR-0044** (zone offset only outside the viewer's zone), **ADR-0045** (layered consent). No ADR for `welcomed_at` (§6).

## 1. Overview: five stages, one pull request each
| Stage | Surface | What ships |
|---|---|---|
| **1** | Bot | Front door on the first `/start`; Today screen with four buttons; three buttons after "Practiced"; one role-aware Menu; five listed commands; task-based `/help`, bot tour retired; five-row `/settings`; free text opens the Menu; short consent screens with "Details"; the zone-label rule in the bot; the Mini App opens straight on the create-shala form (`?open=new-shala`). **Build-ready below (§2–§9).** |
| 2 | Mini App shell | Bottom tabs Today / Practice / Shala and a gear; Today tab with the three-choice day card, one "next step" card, today's class, next moon day. |
| 3 | Mini App | Practice tab (month first) and Settings (five basics, five short pages). |
| 4 | Mini App | Shala tab: people, classes, announcements, invites; two-field shala setup with a checklist; class editing. |
| 5 | All | One word per thing in both languages; guides, screenshots, notes. |

**Out of all five:** one link that both joins a shala and asks a teacher there to accept the student (planned elsewhere; the shala-join flow keeps its structure). No stored role, no analytics, no broadcast about the change, no per-user command menus, no change to what a teacher or a shala sees.

## 3. Domain, use cases, ports
- **Has seen the front door: `account.welcomed_at timestamptz NULL`** (migration, §6). Derivation alone cannot give "shown once": a teacher whose students have not joined yet has no activity and would meet the front door on every `/start`.
- **Domain (pure).** `Account.welcomed: bool`. New `domain/journey.py`: `front_door(account, has_days) -> bool` = not welcomed and none of `teaches`, `main_teacher`, `shala`, `has_days`; `MenuItem` (enum, fixed order) and `menu_for(account) -> tuple[MenuItem, ...]`; `OTHER_REASONS` (the T1 grouping, shared with stage 2's day card). All from the loaded account: no read. New `domain/time_label.py` (ADR-0044). `domain/check_in.py`: `offer_mood_row` is replaced by `entry_shown(existing, enabled)` (Q313).
- **Use case.** `application/accounts.py::MarkWelcomed.execute(principal) -> Welcome(first: bool, active: bool)`. Called only while `welcomed` is false: by `/start` without a payload (then F0, or T0 with `today-menu-hint` when active), and by an invite `/start`, concurrently with the preview read (so the front door is never shown later).
- **Port.** `AccountRepository.mark_welcomed(account_id, at) -> bool | None`: one statement, `UPDATE … SET welcomed_at = :at WHERE id = :id AND welcomed_at IS NULL RETURNING EXISTS(day_log of this account)`; `None` = already set (a double `/start` shows T0 the second time).
- **Reused as they are:** `GetDays`, `SetDayStatus`, `GetPracticePresets` (is there a previous practice), `CopyLastPractice`, `AnswerPracticeOffer`, `UpdateProfile`, `GetInvite`, `PreviewInvite`, the shala preview. If `upsert` does not return the day's stored practice, extend its `RETURNING` rather than add a read (to check when building).
- **`TimeArg.viewer: str | None = None`**; `screens.zone_label(…, viewer)`. Every bot call site passes `account.timezone`: `practice.py` summary, `remind.py` and `moon.py` status lines, `classes.py` (header, day rows, second labels), `attendance.py`, `shalas.py` card. Zone descriptions keep the full form (ADR-0044).
- **API: none.** OpenAPI is unchanged; no new policy (every screen shows the caller's own data).
- **Bot modules.** New `bots/telegram/home.py` + `home_callbacks.py` (F0–F3, M0, M1, H0, `/help`, `/menu`, the free-text and non-admin `/admin` reply through one function). `start.py` keeps `/start` and legacy `o1:`. `tour.py` is deleted; `tour_callbacks.decode` stays for old buttons. One `app_url(base, open, **params)` helper in `screens.py` replaces the three hand-built URLs and fixes the plain URL at `teacher_links.py` ~599.
- **Mini App.** `App.tsx`: `?open=new-shala` → the `links` view with the create form open and focused, Back to Home; `?open=practice` → the `stats` view (stage 2 maps it to the Practice tab). `Links` gets a `create` prop passed down to `Shalas`. Unknown values open Home, as today. `open` values are a contract: old messages keep their URLs.

## 7. Cross-cutting checks
- **Time zones ✔.** T0 prints the date, from the provisional zone while the zone is unknown (unchanged edge, `06 Time Zones`). The zone tip leaves the saved screens (Q314); the reminder reply and the Settings city row say when a zone is missing. The one-tap reminder time is guessed from the provisional zone, and sending still waits for a real one. `help-earlier-day` and `d1:r` carry absolute dates; only `w1:n` is relative, and it writes nothing. Zone labels: ADR-0044, bot in this stage.
- **Privacy ✔.** A front-door tap is navigation: nothing stored, nothing logged; "Invite students" creates the same reusable invite code that opening the invite screen always did, which is not a role. 🌸 moves off the first screen into "Other reason" and still follows `hide_ladies`; T0 shows the owner's own status as the saved screens already do (ashtanga-expert to confirm the 🌸 line). Consent: ADR-0045; the full texts and `quiet_note_agreed` are untouched. A non-admin's `/admin` stays byte-for-byte the reply to any typed text (ADR-0042), now the Menu. Typed text is still never stored.
- **i18n ✔.** Every string in `bot.ftl`, en + ru, key parity; no text in code. Labels fit one per row at 320 px in Russian; every callback ≤ 64 bytes. The front-door path and the Menu row both say "My practice" but lead to different places: separate keys, so stage 5 can settle the word without code.
- **Responsiveness ✔.** Menu, Help, front-door inner screens, Other reason, Settings and More render from the account alone (0 statements). 🧘 goes from 3 statements to 2. Settings goes from 1 to 0. No new import. Layering: `journey` and `time_label` are pure domain; aiogram only in `bots/telegram/`; import-linter unchanged.
- **Tone.** The prompt stays "Practice or rest? Both go in your log."; no "Did you practice today?". ux-writer and ashtanga-expert review all new copy before the final suite.

## 11. Questions for the owner (the bold recommendations are what stage 1 builds)
- **Q310. Who sees "For teachers and shalas" in the Menu?** Read literally, "neither students nor a shala" hides it from a student who joined a shala, which will be most students. **Recommended: show it to everyone who has no students and is on no shala's staff** (ID-03's "not a teacher"); the Menu still has at most eight rows.
- **Q311. The "confirm only if you know this person" line.** ADR-0030 keeps it on the consent screen permanently; "three lines" would drop it. **Recommended: keep it as a fourth short line** on all three consent screens.
- **Q312. Does ✅ on the short screen agree to everything in the full text, the quiet note included** (ADR-0031 ties `quiet_note_agreed` to a confirmed text that names the note)? **Recommended: yes, and the short "sees" line names every data item, the note among them**; what the teacher can do (mark an asana, announcements) stays in Details. ADR-0045.
- **Q313. What `offer_check_in` means now.** The inline mood row is gone. **Recommended: the setting shows or hides the "How do you feel?" button** (stored values kept, default shown; an existing check-in always stays editable); it moves under Settings → More. Alternative: retire the setting.
- **Q314. The time-zone tip.** Without it on saved screens, a bot-only person near midnight may log on the neighbouring date and not learn why. **Recommended: no tip on saves; say it once in the reminder reply and on the Settings city row**, and accept the edge as before the tip existed. Alternative: show it on the first saved screen only (needs one more stored flag).
- **Q315. Existing people after the release.** **Recommended: Today with the one-time line "everything else is under Menu" for people with activity, the front door once for people without, no broadcast.**
- **Q316. Guides in stage 1.** The site build breaks when the tour key and five commands leave. **Recommended: stage 1 updates the bot parts of the pages in §9 and re-shoots the bot screenshots (`/guide-update UI-06`); stage 5 does the wording sweep.** Alternative: only the build fix now, leaving the guide describing the old bot until stage 5.
